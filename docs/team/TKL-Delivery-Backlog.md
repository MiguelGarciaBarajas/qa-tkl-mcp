# TKL Complete Delivery Backlog

## Purpose

This is the authoritative executable plan from the current repository state to a
production-ready TKL MVP. A contributor should not need to invent the next feature or ask
what to do after identifying themselves.

The backlog defines:

- Task order and dependencies.
- Owner and owned paths.
- Required implementation output.
- Required verification.
- Completion evidence.
- External dependencies that may block only live validation.

## Status Rules

| Status | Meaning |
|---|---|
| `DONE` | Implementation, tests, documentation, and handoff evidence are complete |
| `READY` | Dependencies are complete; the owner can start immediately |
| `IN PROGRESS` | An owner is actively implementing the task |
| `BLOCKED-DEPENDENCY` | Another backlog task must complete first |
| `BLOCKED-EXTERNAL` | Only live validation is waiting for access or approved values |

When starting work, change one owned `READY` item to `IN PROGRESS`. When finishing, mark
it `DONE` and add a PR/test reference in the Evidence column. Do not mark a task `DONE`
because a file or scaffold exists.

If live access is unavailable, complete the fixture/contract portion and keep only the
live validation task `BLOCKED-EXTERNAL`.

## Definition of 100%

The MVP is 100% only when all of these are true:

1. Jira, GitHub, and TestRail can ingest approved read-only data incrementally.
2. Raw evidence is normalized into product-scoped canonical knowledge with provenance.
3. Jira requirements link to TestRail manual tests and GitHub automated tests.
4. Coverage, conflicts, and execution freshness use documented business rules.
5. The deployable API uses the real application/knowledge service, not an empty service.
6. The MCP gateway uses the API/application layer with one consistent scoped contract.
7. The dashboard uses the real API by default; mocks remain test/development-only.
8. Fixture-based and approved live-source vertical slices pass.
9. Authentication, authorization, tenant/product isolation, audit, secret handling, and
   untrusted-content protections are verified.
10. Golden-dataset evaluation, runbooks, CI quality gates, deployment configuration, and
    stakeholder acceptance are complete.

## Dependency Release Rules

When a task is marked `DONE`, immediately review tasks that depend on it:

1. If every dependency is `DONE`, change that task to `READY`.
2. If only live access is missing, use `BLOCKED-EXTERNAL`.
3. If implementation work remains, use `BLOCKED-DEPENDENCY`.
4. Never leave a task blocked merely because another owner has not sent a message; verify
   the dependency from merged code and tests.

## Required PR Evidence

Every implementation PR must include:

- Backlog task ID and owner.
- Problem and expected behavior.
- Files/modules changed.
- Contract and security impact.
- Tests and commands executed.
- Sanitized evidence for user-visible behavior.
- Updated backlog status/evidence.
- Explicit follow-up tasks not included.
